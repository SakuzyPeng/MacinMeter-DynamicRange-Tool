# ADR-0001：以 0.2.0 重建可信主干

- 状态：Accepted
- 实施状态：DONE
- 日期：2026-07-18
- 决策范围：M0
- 相关路线图：[架构整改与参考插件重新对齐路线图](../ARCHITECTURE_AND_REFERENCE_ALIGNMENT.md)
- M0 时临时算法规格（现为已取代的历史基线）：
  [Provisional v1](../../reference/specs/provisional-v1.md)
- 后继并发修订：
  [ADR-0014](0014-deterministic-decode-analysis-pipeline.md) 已解除 post-M6 对窗口级、
  packet 级与文件级并行的一刀切硬禁令。本文的串行要求仍准确描述 M0 基线，不再
  作为当前阶段的永久禁令。

## 背景

0.1.x 已证明了多格式流式解码、在线窗口统计、CLI 和 Tauri 复用 Rust
代码等方向可行，但现有生产路径同时存在以下问题：

- 公共 `AppConfig` 混合算法、解码、并发、输出和 UI 选项；
- CLI、GUI 和库入口没有共享一份稳定的请求、结果和错误模型；
- 两套 DR 状态和多条格式/声道分支产生不可解释的结果差异；
- 包级并行、EdgeTrimmer 和部分外部解码路径尚不满足可信生产契约；
- JSON、批处理退出码和输出副作用不适合作为自动化接口；
- 0.1.x 的现有输出不能作为参考插件兼容性的正确性依据。

继续以 0.1.4 补丁逐处修补，会把旧模块边界、旧 CLI 行为和错误的公共
抽象带入后续版本。项目尚未进入 1.0，因此现在应优先建立长期可信边界，
而不是保留不可靠行为的兼容性。

## 决策

M0 不再是 0.1.4 止血补丁，而是目标版本 **0.2.0** 的可信主干重建。
0.2.0 允许公共 Rust API、CLI、JSON 和 GUI IPC 发生 breaking change，
不提供 0.1.x 兼容层或旧命令别名。

M0 采用以下单向依赖：

```text
domain
├── analysis
├── codecs
└── application(macinmeter) -> analysis + codecs
                              ├── CLI
                              └── Tauri
```

各层职责如下：

- `domain`：有效类型、分析报告、稳定错误码和不含 I/O 的领域规则；
- `analysis`：唯一生产分析状态机，仅消费已验证的 PCM 数据；
- `codecs`：探测、解码计划和统一 PCM 源契约；
- `application`：文件发现、单文件/批处理编排、取消和进度；
- adapters：参数解析、JSON/人类可读渲染、文件写入和 Tauri IPC。

## M0 公共契约

M0 的公共 Rust API 以具名请求和结果为中心，不公开 CLI 配置、长元组结果、
formatter helper、accumulator 或重复引擎。唯一受约束的低层状态机
`AnalyzerSession` 是刻意公开的流式分析入口。核心报告至少区分：

- 源文件与实际 PCM 流信息；
- 每声道测量结果；
- 聚合结果及明确的声道排除原因；
- 解码诊断；坏媒体不会产生 partial 成功报告，批量部分成功由 tagged item outcome
  和 `BatchStatus` 单独表达；
- 稳定 `ErrorCode`、失败阶段和可选 backend/path 上下文。

算法计算与展示策略必须分离。是否显示 RMS/Peak、是否隐藏警告、输出路径和
终端详细程度都不是分析配置。LFE 布局未知时不得通过声道数猜测并静默改变聚合。

## CLI 与 JSON

0.2.0 CLI 使用显式操作，不再根据路径类型或“无参数双击”猜测模式：

```text
macinmeter analyze FILE
macinmeter batch INPUT...
```

M0 约束：

- stdout 只承载请求结果；横幅、进度和诊断只进入 stderr；
- 未指定输出文件时不产生隐式报告文件；
- 单文件和批处理使用同一领域结果，批量一个文件仍是批量响应；
- JSON 使用独立的 `schemaVersion`，不把软件版本当作 schema 版本；
- JSON 序列化失败必须返回错误，不允许回退为空对象；
- 批处理结果显式区分全部成功、部分成功、全部失败和取消；
- 进程退出码只表达操作结果，具体原因由结构化错误码表达。

M0 实施时的 JSON schema 为 provisional。稳定前只允许向当时的
[`reference/specs/provisional-v1.md`](../../reference/specs/provisional-v1.md)
记录的契约收敛，不从 0.1.x JSON 反向推导兼容要求。

## M0 默认能力

可信基线优先于性能和格式数量：

- 包级并行默认关闭，M0 公共 CLI 不暴露其批大小或线程调参；
- 批处理先以确定性串行语义为基准，并发只能在同一应用调度器下恢复；
- EdgeTrimmer 不进入 M0 生产分析管线、公共请求或结果 schema；
- 静音过滤等增强不能冒充参考算法，进入生产前必须成为显式前处理阶段；
- M0 只保留安全标量路径；SIMD 在有明确收益、统一语义和差分测试后再引入；
- 首批 codec 可以收窄，但每个声明支持的路径必须满足共同解码契约。

## 适配层处置

新纵向路径可运行后，旧入口直接删除，不长期维护双轨：

- 删除以 `AppConfig` 为公共 API 的入口；
- 删除库/application 层中的直接打印、Markdown 拼接和文件写入；
- 删除单文件目录特判和自动保存路径；
- 删除 CLI 与 Tauri 各自维护的结果和错误 DTO；
- 删除 Tauri 进程级取消标志和运行时修改 FFmpeg 环境变量的做法；
- 生产切换后删除重复 DR 状态机，而不是保留 legacy profile。

0.1.x 只作为观察重构差异的 legacy snapshot，不是 0.2.0 的兼容目标。

## 工程门禁

M0 施工期间，远程 CI 暂时缩减为手动触发的单 Ubuntu workspace job，仅执行：

1. workspace format check；
2. workspace Clippy；
3. workspace tests。

本地 pre-commit 只执行 format check 和 `cargo check --locked --workspace`，提供快速、
无额外审计工具依赖的反馈。安全审计、多平台构建、GUI 打包和发布自动化并未
被判定为不需要，而是在 workspace 和依赖边界稳定后作为独立里程碑恢复。

## 完成条件

M0 只有在以下条件全部满足时才能从 `DOING` 变为 `DONE`：

- 0.2.0 workspace 的依赖方向可由包边界检查；
- 所有生产入口调用唯一分析状态机和唯一结果构造逻辑；
- 默认路径不存在已知静默截断、公开安全 API UB 或 EdgeTrimmer 误删；
- 同一 PCM 在不同合法 chunk 切分和声道数量下满足已记录工程不变量；
- CLI JSON 可直接解析，stdout/stderr 和退出码有黑盒测试；
- 批量全部成功、部分失败、全部失败、取消和输出失败均有结构化结果；
- CLI 与 Tauri 通过同一 application API 和 wire DTO；
- reference 目录能区分工程不变量、参考观测、算法规格和 legacy snapshot；
- 0.2.0 的用户声明不超出当前证据。

## 后果

正面后果：

- 现在就缩小公共 API，避免错误边界成为长期兼容负担；
- 正确性、参考研究、CLI 和 GUI 可以围绕同一报告模型推进；
- 并发、增强前处理和更多 codec 可以在稳定契约上逐项恢复；
- 版本号明确传达 breaking change。

代价：

- 0.1.x 调用者、脚本和 GUI IPC 需要迁移；
- 施工期支持格式、性能和自动发布能力可能暂时减少；
- 在旧代码删除前会有短期迁移适配，但它不构成公共兼容承诺。

## 未采用的方案

### 发布 0.1.4 并逐处修补

拒绝。它无法消除 `AppConfig`、双结果模型、输出副作用和重复批处理编排，
且 patch 版本不能清楚表达公共契约重置。

### 长期保留 legacy profile

拒绝。现有输出没有独立 oracle，保留它只会扩大测试和产品语义表面。

### 先恢复所有性能优化和格式，再重构

拒绝。当前并发与 backend 行为尚未满足统一终态和错误传播契约，优化会放大
不可解释状态空间。
