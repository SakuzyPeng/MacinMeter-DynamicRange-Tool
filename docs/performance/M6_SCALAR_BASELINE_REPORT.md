## 结论

M6 已经得到第一份可复核的 0.2.0 安全标量/串行基线。它建立了后续比较的零点，但
没有形成跨机器性能承诺，也没有证明应当恢复文件级并发、SIMD 或其他执行路径。

当前最值得 sampling profile 的两个 scope 是：

1. direct `AnalyzerSession`：它在 WAV/AIFF/float64 application 路径中占据显著
   工作量，且是所有格式共享的优化杠杆；
2. FLAC decode：同源 PCM 下，它的 decode 时间明显高于未压缩格式，并主导 FLAC
   application 路径。

当前数据不支持先做文件级并发。8-track 串行 batch 的单位音频成本与单文件 WAV
application 基本一致，没有出现额外 scheduler/discovery 瓶颈；是否需要并发仍需
真实用户规模、较慢设备或更重 codec workload 的需求证据。

64 声道 direct analysis 的 native max RSS median 为 5.28 MiB，与每声道固定
histogram 状态相符；本基线没有暴露随时长增长的内存问题。duration-independent
内存仍由产品 invariant test 证明，不能由单次 RSS 取代。

## 波动与复核

canonical run 不删除任何 outlier。多数 case 的 MAD 小于 1.3 ms；WAV s16 decode、
64ch analysis 等各出现一个保留的较慢样本，导致 min–max span 高于 MAD 所表达的
典型波动。

在同一 clean source 上先进行过一轮完整非 canonical 复核：

- raw SHA-256：`db41bd38d2c9bb63d221b634f518a477e4ade25e5041f3dbf6ccaf65958bf396`；
- 15 个 result fingerprint 与 canonical run 全部一致；
- 15 个 case 的 median 与 canonical run 的差异绝对值均不超过 1.83%。

该复核运行保留在本机 ignored `target/performance-results`，不作为仓库原始证据；
本报告的数值只取 committed canonical record。

## 明确不能得出的结论

- 不能把这些吞吐写成产品保证或其他机器的预期；
- 不能声称 cold-cache、慢盘、网络盘或任意真实音乐库具有同样结果；
- 不能从 synthetic repeated-block corpus 推断所有 FLAC 压缩复杂度；
- 不能把 process RSS 当作文件 cache、系统总内存或未来多进程总预算；
- 不能因 batch 很快就永久排除文件级并发，也不能据此立即恢复并发；
- 不能因 direct analyzer 占比显著就预设 SIMD 是正确解法；
- 不能用两个独立 run 的小差异代替同 run interleaved A/B。
